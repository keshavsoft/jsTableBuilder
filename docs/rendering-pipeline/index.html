TableBuilder Configuration Architecture

1. Purpose

Configuration is the primary public contract of TableBuilder.

The public configuration should describe what the consumer wants without exposing internal implementation conventions.

2. Public Configuration

The preferred public shape is clean and semantic. 

{
    htmlId: "table-root",

    data: [],

    columns: [],

    theme: "style1",

    tableOptions: {
        commonOptions: {},
        headOptions: {},
        bodyOptions: {},
        footOptions: {}
    },

    topHeader: {},

    endPoints: {}
}

3. Internal Configuration

Internally, the project uses the in prefix convention.

Example: 

{
    inCommonOptions: {
        inTableWidth: "100%",
        inTableBorder: "1px solid #e5e7eb"
    }
}

This internal representation should not be forced onto public consumers.

4. Public to Internal Mapping

Public Config
     |
     v
mapTableOptions
     |
     v
Internal Config

The mapping layer translates the clean public API into the internal naming convention.

5. Why Two Configurations Exist

The two representations serve different audiences.

Configuration Purpose
Public configuration Simple API for consumers
Internal configuration Strict internal processing convention

6. Default Configuration

The default configuration should be the primary description of the supported configuration structure.

It should provide safe defaults for:

  • Table identity
  • Data
  • Columns
  • Theme
  • Table options
  • Header options
  • Body options
  • Footer options
  • Top header
  • Endpoints

7. Endpoint Configuration

Data sources should eventually be described through configuration.

Example: 

endPoints: {
    read: "/api/customers",
    create: "/api/customers",
    update: "/api/customers",
    delete: "/api/customers"
}

Endpoint names should describe intent.

Avoid ambiguous names such as: 

read1
read2
read3

Prefer meaningful names.

8. Static Data and Remote Data

The architecture should support both: 

data: []

and: 

endPoints: {
    read: "/api/data"
}

The renderer should not care where the data came from.

10. Defaults API

The library should expose a discoverable representation of its defaults.

A future API may look like: 

TableBuilder.getDefaults()

The purpose is to allow developers and AI systems to understand the expected configuration shape without reading implementation files.

11. Validation API

Validation should be a separate responsibility.

A future API may look like: 

validateConfig(config)

It should identify invalid or incomplete configuration rather than silently inventing missing values.

12. Column Configuration

A column should describe both its data identity and presentation. 

{
    dataKey: "customerName",
    header: "Customer Name",
    isVisible: true,
    options: {
        width: "200px",
        align: "left",
        vAlign: "middle"
    }
}

13. Data Key vs Caption

These are different concepts. 

dataKey: "customerName"
header: "Customer Name"

dataKey identifies the source property.

header identifies the human-readable UI caption.

14. Configuration as Source of Truth

The long-term architecture should move toward: 

Configuration
      |
      +--> Data
      +--> Columns
      +--> Classes
      +--> Behavior
      +--> Endpoints
      |
      v
Rendering Engine

This allows the same configuration to drive multiple visual renderers.

15. Multiple Renderers

Future renderers may include:

  • Table
  • Vertical
  • Card

The configuration should describe the information rather than encode one specific visual representation.

16. Configuration Design Rule

Configuration should describe intent, not implementation details.
