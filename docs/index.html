jsTableBuilder is a browser-first JavaScript library that converts JSON data and column configuration into reusable HTML table interfaces. This page is the single source of truth for what the repository does, how it is organized, and where it is going.

The core idea

01 / Purpose

A reusable table system for changing data screens

Applications often repeat the same table work: create headers, order fields, render rows, add search, handle sorting, calculate summaries, and keep styling consistent. This repository moves those decisions into data and configuration so the rendering engine can be reused across reports, admin screens, dashboards, and internal tools.

Records+Columns+Options→TableBuilder→DOM table

02 / Current capabilities

What the repository does today

Data-driven rendering

Accepts arrays of objects and turns configured fields into table rows and cells.

Configurable columns

Supports headers, keys, width, alignment, sortable columns, and summary behavior.

Search and sorting

Provides a top-header search flow and single or multi-column sorting from header interaction.

Table controls

Configures width, borders, serial numbers, header and row heights, and optional footers.

Themes and classes

Includes built-in style profiles and class overrides for projects with their own visual language.

Browser and CLI paths

Works as source modules and includes package metadata for NPM use and source scaffolding.

03 / Runtime model

How configuration becomes a table

1. Construct. The consumer creates TableBuilder with an element ID, data, columns, options, theme, and optional endpoints.

2. Prepare. Public option names are mapped to internal names. Defaults are applied, sizes are normalized, and data is placed in the instance store.

3. Compose. The table, header, body, footer, and empty state are built by focused modules under buildTable/.

4. Interact. Header events call sorting; the top header calls search; cell content can be handled by the Web Component layer.

04 / Repository map

Where each responsibility lives

The root files represent the current implementation. The archive/ directory contains earlier versions and is useful for understanding how the design evolved, but it is not the first place to add new behavior.

05 / Public API

The configuration contract

const table = new TableBuilder({
    htmlId: "table-root",
    data: [{ name: "Ada", role: "Engineer" }],
    columns: [
        { dataKey: "name", header: "Name" },
        { dataKey: "role", header: "Role", options: { sortable: true } }
    ],
    tableOptions: {
        commonOptions: { showSerialNo: true, tableWidth: "100%" },
        footOptions: { showFooter: true }
    },
    topHeader: { label: "Team directory", placeholder: "Search..." }
});

table.appendToDom();

06 / Direction

What we will build next

The repository already has the separation needed for a larger table platform. Future work should strengthen the public contract and quality around the existing architecture rather than bypassing it.

Stabilize the API

Document and validate column options, endpoint behavior, error states, and the supported version selected by consumers.

Make tests executable

Cover configuration mapping, search, sorting, empty data, summaries, and DOM output with repeatable browser or unit tests.

Improve data sources

Formalize read and mutation endpoints, loading states, failed requests, and refresh behavior without coupling renderers to transport.

Grow cell components

Expand reusable renderers for links, dates, currency, badges, actions, and safe custom content.

Unify distribution

Clarify the relationship between source modules, bundled browser output, NPM entry points, and the CLI scaffold.

Retire ambiguity

Keep historical versions for reference while making the current implementation, examples, and release policy unambiguous.
