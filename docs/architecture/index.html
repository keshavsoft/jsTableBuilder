TableBuilder Architecture

1. Purpose

TableBuilder is being designed as a configuration-driven frontend rendering library.

The long-term goal is not simply to build tables. The goal is to create a predictable rendering system where configuration, data, builders, components, and DOM responsibilities are clearly separated.

3. Configuration Layer

The public configuration should be clean and understandable. It must not expose internal naming conventions.

Internally, the configuration can use a stricter naming convention and structure.

A mapping layer is responsible for converting public configuration into the internal representation.

4. TableBuilder Responsibility

TableBuilder should act primarily as an orchestrator.

It should not contain detailed DOM-building logic.

Its responsibilities include:

  • Accept configuration.
  • Initialize internal state.
  • Prepare configuration.
  • Prepare or retrieve data.
  • Delegate rendering.
  • Expose the resulting DOM to the consumer.

5. Builder Responsibility

Builders are responsible for creating and composing DOM structures.

A builder should have one clear responsibility.

Examples:

  • Table builder — composes the table.
  • Header builder — composes the table header.
  • Row builder — creates a row.
  • Cell builder — creates a cell shell.

6. Web Component Responsibility

Web Components should own reusable UI behavior and content rendering.

The builder should not become responsible for every detail of the content displayed inside a cell or header.

The intended relationship is: 

Builder
   |
   v
DOM Shell
   |
   v
Web Component
   |
   v
Actual UI Content / Behavior

7. DOM Ownership

Each builder creates its own DOM element and returns it.

Higher-level builders compose the returned elements.

Consumers should not need to understand the internal DOM structure.

8. Composition

Future renderers may include:

  • Table
  • Vertical
  • Card
  • Other future views

These renderers should consume the same conceptual configuration wherever practical.

A future higher-level composition layer may combine multiple renderers.

10. Main Architectural Rule

Do not put responsibility in a higher layer when a lower layer clearly owns that responsibility.

For example, alignment belongs to cell rendering rather than row orchestration. Header content belongs to the header content component rather than the table builder.

11. Migration Philosophy

The current working implementation should be treated as a reference implementation.

New architecture should be introduced incrementally rather than through one large rewrite.

  1. Document the existing pattern.
  2. Standardize folder entry points.
  3. Standardize naming conventions.
  4. Centralize Web Components.
  5. Introduce configuration validation.
  6. Improve configuration normalization.
  7. Improve data-source handling.
  8. Introduce additional renderers.
  9. Evaluate migration from older implementations.
