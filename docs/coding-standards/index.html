TableBuilder Coding Standards

1. Purpose

These rules exist to make the source code predictable for both humans and AI-assisted development.

The objective is that a developer can look at a function and immediately understand where every variable came from and what responsibility the function owns.

2. Folder Entry Point Rule

Every functional folder should expose its public entry through: 

index.js

Example: 

forHead/
    index.js
    v1/
    v2/

forBody/
    index.js
    v1/
    v2/

Consumers should preferably enter a folder through its index file rather than knowing the implementation file names.

3. Versioned Implementations

When a component requires multiple implementations, versions should be separated explicitly. 

forBody/
    index.js
    v1/
        TableBody.js
    v2/
        TableBody.js

Version selection should be explicit.

Do not automatically determine the latest version by scanning folder names.

4. Function Input Naming Convention

Every value received by a function as an input must use the in prefix.

Example: 

function buildTable({
    inData,
    inColumns,
    inClasses
}) {

The in prefix communicates:

This value came from outside this function.

5. Immediately Create Local Variables

Inputs should be immediately mapped to local variables at the beginning of the function. 

function buildTable({
    inData,
    inColumns,
    inClasses
}) {
    const localData = inData;
    const localColumns = inColumns;
    const localClasses = inClasses;

    // ...
}

This establishes a clear visual distinction between external inputs and variables belonging to the current scope.

6. Meaning of `in` and `local`

The naming convention creates a simple variable life-cycle model. 

External Input
     |
     | inData
     v
Local Representation
     |
     | localData
     v
Function Processing

Therefore:

  • inSomething means an incoming function argument.
  • localSomething means the local representation of that input.
  • A variable without either prefix should normally be a value created inside the current scope.

7. Why This Convention Exists

The purpose is not JavaScript syntax. It is code readability.

When reading a large function, a developer should be able to distinguish: 

const localColumns = inColumns;

from: 

const visibleColumns = localColumns.filter(...);

The first is an input mapping. The second is a value created by the current function.

8. Avoid Hidden External Variables

Functions should not depend on undeclared or mysterious external values when those values can reasonably be supplied as inputs.

Prefer: 

function buildCell({
    inCellValue,
    inOptions
}) {
    const localCellValue = inCellValue;
    const localOptions = inOptions;
}

9. Arrow Functions

Arrow functions are the preferred function syntax throughout the implementation.

Example: 

const prepareData = (inData = []) => {
    const localData = inData;

    return localData;
};

This should be used consistently unless there is a specific technical reason to use another function form.

10. Export Style

Prefer defining the implementation first and exporting it at the bottom of the file. 

const buildTable = ({
    inData
}) => {
    // implementation
};

export {
    buildTable
};

This keeps the implementation visually separate from the module's public API.

11. Default Values

Default values should be explicit and close to the responsibility that owns them. 

const DEFAULT_OPTIONS = {
    width: "",
    align: "",
    vAlign: ""
};

Shared defaults should be centralized when they are genuinely shared.

12. Single Responsibility

Each file should have one understandable responsibility.

Avoid creating a large function that:

  • fetches data,
  • normalizes configuration,
  • creates DOM,
  • attaches events,
  • formats values,
  • and manages application state.

Separate those responsibilities.

13. Builder Pattern

Builders should primarily:

  • create DOM shells,
  • delegate children,
  • compose returned DOM elements,
  • return their completed element.

14. Collection Appender Pattern

When a builder needs to process a collection, a dedicated append helper may own the iteration. 

buildHeaderRow
    |
    +--> appendHeaderCells
            |
            +--> buildHeaderCell

This keeps iteration separate from element creation.

15. Web Component Pattern

Builders should create Web Components when the component owns reusable UI behavior or content rendering. 

const contentElement =
    document.createElement("ks-table-cell-content-common");

contentElement.inputs = {
    cellValue: localCellValue,
    rowData: localRowData,
    options: localOptions
};

Components should receive structured inputs rather than relying on hidden global state.

16. No Premature Generalization

Do not create one generic component merely because two components look similar today.

First establish the independent implementations. Generalize only when the shared behavior is proven.

17. AI Development Rule

AI-generated changes must first identify the existing responsibility and follow the established pattern.

AI should not invent a new naming convention, folder convention, export style, or component pattern without a documented reason.

18. Golden Rule

Make the source code predictable enough that another developer or AI does not need to guess your architectural intention.
