TableBuilder Versioning Strategy

1. Purpose

Versioning exists so that new implementations can be developed without immediately destroying a working implementation.

2. Folder-Based Versions

A component or renderer may contain multiple versions. 

forBody/
    index.js
    v1/
        TableBody.js
    v2/
        TableBody.js

The same approach can be used for:

  • Header
  • Body
  • Footer
  • Table
  • Future renderers

3. Index as Folder Entry Point

Every functional folder should expose its entry through index.js.

The index file is the stable access point. 

consumer
    |
    v
folder/index.js
    |
    v
selected implementation

4. Explicit Version Selection

Version selection should be deliberate.

The index may expose explicit versions: 

export const v1 = {
    buildTableBody: buildTableBodyV1
};

export const v2 = {
    buildTableBody: buildTableBodyV2
};

export const buildTableBody = buildTableBodyV2;

5. Default Version

A default version may be provided.

However, the default should mean:

Recommended implementation for the current release.

It should not simply mean:

Highest numbered folder.

6. Avoid Automatic Highest-Version Discovery

Do not scan the filesystem and automatically select: 

v3

merely because it has a higher number than: 

v2

Automatic selection creates invisible behavior changes.

7. Why Version Folders Are Useful

Version folders allow experimentation. 

v1
 |
 +-- Stable implementation

v2
 |
 +-- New implementation

v3
 |
 +-- Experimental implementation

A new version can be evaluated without modifying the existing version.

8. Migration Strategy

  1. Create the new version.
  2. Keep the old version intact.
  3. Compare behavior.
  4. Test the new version.
  5. Make the new version the recommended default only when ready.
  6. Keep the old version available while migration is required.

9. Versioning and AI Development

Versioned folders are particularly useful when working with AI.

An AI can be instructed: 

Modify v2 only.
Do not change v1.
Follow the architecture used by v2.

This dramatically reduces the risk of accidentally changing stable code.

10. Versioning Rule

Preserve working implementations while developing new architectural ideas. Promote a version only after its behavior and architecture are understood.
